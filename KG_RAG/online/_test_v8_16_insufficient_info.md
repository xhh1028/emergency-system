## 一、先复现（**你的结论完全成立**）

输入：`某地铁站出事了，你处理一下。`

| 层 | 实际 |
|---|---|
| 上游 | `事件类型：未识别`、`位置：未识别`、**无事故等级** |
| 定级段 | 初判 = **无法初判** ✅、精确判定 = **尚未成立** ✅、响应 IV级（保守）✅ —— **定级层是诚实的** |
| **处置段** | **仍然输出了方案**（本次 11 步；你那次 15 步） |
| **依据** | **11/11 全部来自 `AIEP28 28C`（处理车站水淹）** —— 场景匹配不到，兜底拉取，LLM 硬套 |

**"万能模板"的铁证**——步骤 1 原文：

> `值班站长组织车站员工对事件现场实施先期处置：**若涉及水淹则实施挡水/排水，若涉及火灾则使用灭火器扑救，若涉及人员受伤则实施现场…**`

**不知道该做什么时，把所有可能都列一遍**——这不是方案，是在赌。
而每一步的「依据」都挂着一份**与事件无关**的规章（车站水淹）——**读者照着执行，比不输出更危险**。

## 二、改动：两道门（prompt + 代码）

### 门 1｜prompt 前置条件（`generate_plan` 的 prompt，在【硬性约束】之前）

```
【前置条件：是否生成方案】
若满足以下任一条件，禁止生成具体处置步骤——steps 必须为空数组 []，
并在 severity.conclusion 里照实写清缺什么，不得用"万能模板"凑步骤：
1. 主事件类型为"未识别"或为空；
2. 你无法从描述中判断这是什么事件（如"某地出事了""处理一下"这类没有具体信息的描述）；
3. 没有任何可支撑动作的场景信号（火灾/爆炸/脱轨/撞击/拥挤/袭击/设备故障/人员伤病…一个都没有）。

理由：无法识别事件时硬套规程，比不输出更危险……
反例（明确禁止）：事件性质未知时写"步骤1：若涉及水淹则挡水、若涉及火灾则灭火…"
若事件可识别（哪怕信息不完整，例如"站台有乘客晕倒""区间列车起火"），照常生成完整方案。
```

### 门 2｜代码前置门（**不依赖 LLM 是否听话**）

新增 `_insufficient_info(event_profile)` → `(是否拦截, 原因)`：
- 事件类型为空/`未识别/未知/无` → 拦截；
- 上游等级为 `未识别/未知/空` → 拦截；
- 两者皆无 → 拦截（原因写明"均未识别"）。

`generate_plan` 里在拿到 `event_profile` 后**立即判**，命中则**直接返回 `_insufficient_plan(reason)`——
连 LLM 都不调用**（省一次调用，且结果**确定性**）。

新增 `_insufficient_plan(reason)` 输出模板：**只有定性说明 + 补充指引，零处置步骤**：

```
## 一、事件定性
- **状态**：**信息不足，无法生成处置方案**
- **原因**：…
- **请补充以下信息后重试**：
  1. 事件性质（火灾 / 爆炸 / 脱轨 / 撞击 / 拥挤踩踏 / 袭击 / 设备故障 …）
  2. 发生位置（车站 / 站台 / 区间 / 隧道 / 出入口 / 车辆段 …）
  3. 已知伤亡或险情（有人受伤 / 被困 / 冒烟 / 起火 / 有异常气味 …）
  4. 当前状态（是否可控 / 是否需要外部力量 / 是否已影响行车）
---
## 二、处置步骤
- **不适用**（信息不足，待补充后重新生成）
```

### 门 2b｜渲染后兜底（`_render_markdown`）

即使用户描述能骗过门 2，只要**方案自己说"无法初判 + 精确判定尚未成立"**，或**模型交了空 `steps`** →
同样**截断**，不渲染"二、处置步骤"。

## 四、副作用与代价（如实说）

1. **门 2 是"任一条件"拦截**——只要**事件类型**或**上游等级**有一个是"未识别"就拒生成。
   风险：上游偶发解析失败时，本可处置的事件也会被拒。**目前无实例，先观察**；
   若日后发现误拦，可收窄为"两者皆无才拦"。
2. **拒生成时不给任何步骤**——用户若确实需要"在信息不足时也要有兜底动作"（如"先保护现场、先报告"），
   现在**一点都没有**。这是**刻意的保守**（宁可不说，不可乱说），但你要知道这个取舍。
