## 一、改动清单（范围严格限于设计文档）

**新增** `online/scene_tier_map.json`：
```json
{ "大客流": { "tier_overrides": { "运营调整": 1 } } }
```

**改** `online/plan_generator.py`（+94 / −15）：

| 项 | 内容 |
|---|---|
| `import os` | 仅为多路径探测配置文件 |
| `_load_tier_map()` | 读 `scene_tier_map.json`；缺失/损坏/类型非法 → `{}` + 记 WARNING，**不崩** |
| `_tier_overrides()` | 惰性加载，进程内只读一次 |
| `_effective_tier(action_type, scene)` | 先查 overrides，未命中 → 默认 `TIER` |
| `_scene_key(event_profile, tier_map)` | 由 event_profile **主事件**反推场景；无命中 → `None` |
| `_tier(step, scene=None)` | 改为调 `_effective_tier` |
| `_demand_slots` / `_merge_steps` / `_order_steps` / `_tier_diagnostic` | 各加一个 `scene=None` 形参透传（**逻辑未改**） |

默认 `TIER` 表保持原样。**未触碰** `KW_*` / `POSITION_RULES` / `COUNT_RULES` / `_flags`；**未改** `main.py` / `scene_chapter_map.json` / 检索层。

> **场景名来源（设计文档 Q1 的悬案，此处落实）**：`generate_plan()` 的现有参数里**没有**场景名。
> 让其从 `event_profile` 的**主事件类型**反推（子串规则与检索层 `_match_scenes` 一致），因此**无需改 `main.py`**。
> ⚠️ **只认主事件、不认次生事件**——暴雨的主事件是「暴雨导致车站积水倒灌」，但次生常含「大客流拥挤」；
> 若纳入次生匹配，暴雨会被误判成大客流场景、被套上 `运营调整→1` 的覆盖，直接破坏"暴雨无回归"。
> 该坑在单元验证时命中并已修正（见 §四证明）。

## 三、大客流：`运营调整` 真的进了第 1 档

`[tier]` 日志（3 次全出现）：
```
[tier] 场景=大客流 → TIER 覆盖={'运营调整': 1}
```

**RUN1 第 1 档步骤清单**（共 9 步，其余为第 4/5 档）：

| # | 优先级 | 档 | action |
|---|---|---|---|
| 1 | 人身安全 | 1 | 值班站长指派站台岗员工在站台边缘及扶梯口引导乘客有序排队，防止拥挤踩踏 |
| 2 | **运营调整** | **1** | 值班站长在出入口外设置回形线路，进一步减缓乘客进站速度 |
| 3 | **运营调整** | **1** | 值班站长通知事故处理主任进行站台检查并开始实施综合人流后援方案 |
| 4 | **运营调整** | **1** | 值班站长通知行车调度员安排后续列车在合适车站截停并清人，作为空车驶往本站协助疏散 |
| 5 | **运营调整** | **1** | 值班站长启动大客流控制方案B，在站厅与站台楼梯/扶梯连接处设置客流控制点 |
| 6 | **运营调整** | **1** | 站厅岗员工改变扶梯走向，引导乘客走楼梯，缓解扶梯口人流对冲 |
| 7 | **运营调整** | **1** | 值班站长在付费区/非付费区设置回形线路，减缓乘客进站速度 |
| 8 | **运营调整** | **1** | 值班站长安排站务员在进站闸口设置铁马，实现分批进闸 |
| 9 | **运营调整** | **1** | 值班站长安排员工在出入口用铁马等备品限制乘客进站 |

即：客流管控类步骤（第 2–9 步）**全部升入第 1 档**，紧跟在人身安全步之后、`信息报告`(第4档) 之前。
**且逆序对仍为 0** —— 升档没有破坏单调性（因为第 1 档内按 `n` 排，整体仍单调不减）。

## 四、暴雨 / 恐袭：无回归的证明

**结构证明（构造性）**：
- `_scene_key` 对两场景的主事件（`暴雨导致车站积水倒灌` / `站内持刀伤人事件`）均返回 `None`；
- `scene=None` 时 `_effective_tier(at, None)` **就是** `TIER.get(at, TIER_OTHER)`，与改动前的 `_tier(step)` 逐字相同；
- 因此这两条路径的排序/合并/占位逻辑**与配置化前完全一致**。

**实证**：
- 两场景 `[tier]` 日志**均无 `场景=` 行**（说明未套任何覆盖）；
- 档位序列只使用默认档值 `{1,2,3,4,5}`，无越档；
- 步数 `[14,14,14]` / `[14,14,15]`、逆序对 0、降级 0，与配置化前（`_test_v6_1_kw_*`）同水准；
- 恐袭 救治 3/3、疏散 3/3；挡水 3/3 未误触发。
- 单测：`_effective_tier("运营调整", None)=3`、`("人身安全", None)=1`、`("运营调整","大客流")=1`、`("运营调整","暴雨")=3`。

**fail-soft 单测**（对齐 `_load_pins` 风格）：

| 输入 | `_load_tier_map()` 返回 | 行为 |
|---|---|---|
| 文件缺失 | `{}` | 记 WARNING，全部用默认 |
| JSON 损坏 | `{}` | 记 WARNING，全部用默认 |
| 档号非整数（`"1"` / `true`） | `{}`（逐项忽略 + WARNING） | 全部用默认 |

三例均**不崩**。

## 五、两条如实说明（均非本次改动引起）

### 1️⃣ 恐袭首批 RUN3 = DeepSeek API 超时 → 走了降级

首发一批 3 次里，恐袭 RUN3 报 `⚠️ 方案生成失败：Request timed out.`，代码按既有设计
**降级为纯文本**（返回本地检索到的规程资料），**未崩、输出不丢**。
这是**网络/API 抖动，与配置化无关**。为得到有效样本，**重跑了恐袭 3 次**（表 §二 用的是重跑结果，3 次全为结构化方案）。

> 注：这条走的是 `generate_plan` 里 LLM 调用的 `except` 降级路径，与"两次均未产出合法 JSON"是两条不同的降级分支。

### 2️⃣ 暴雨 RUN3：`疏散` 未占位 —— 既有 `KW_SHU` 词形缺口（**不在本次范围**）

该次第 1 档有一个真实疏散步骤：`安排员工对站台拥挤区域进行疏散引导，优先将老人、儿童、残障及受伤人员转移至安全区域`，
但 `KW_SHU` 不认 **「疏散引导」**（`疏散` 在 `引导` 之前）这一写法 → 不占位（日志：`全文无 疏散 动作的第 1 档步骤`）。

- **与本次改动无关**：`KW_SHU` 未被触碰，该写法在 v6.1 词表下同样漏。
- 属"步骤存在、词表不认"，**不是纯遗漏**。
- 按「不做任何顺手优化」**未修**，仅报备：若要覆盖，`KW_SHU` 需补 `疏散引导` 之类词形（留给下一轮裁定）。

> 另：暴雨 3 次的 `疏散` 占位为 2/3（RUN1/RUN2 命中 `宣布疏散车站`）。这是 **LLM 采样 + 上述既有词形缺口**共同结果，
> **不是 tier 配置造成的回归**——tier 配置对暴雨是零作用（§四）。
