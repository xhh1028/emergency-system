## 一、Q1：分层表——同意，但只有一格是真的场景相关

| 组件 | 你的分层 | 我的裁定 | 依据 |
|---|---|---|---|
| `KW_*` | 通用 | ✅ **同意** | 已裁定：救治动作到哪都是救治，词表覆盖措辞即可 |
| `TIER`（action_type→档号） | 场景相关 | ✅ **同意** | 大客流实证：`运营调整` 默认第 3 档，但客流管控是该场景的人身安全动作 |
| `POSITION_RULES` 上限值 | 可选场景相关 | ✅ 同意，**但 v1 不配** | 无实证需要覆盖：暴雨 bounds(3,3,5) 在恐袭/大客流也没出问题 |
| `POSITION_RULES` 匹配模式 | 通用 | ✅ **同意** | 匹配模式**就是** `KW_*`，同一裁定 |
| `COUNT_RULES` | 通用 | ✅ **同意** | 防掺水，与场景无关 |
| `_flags` 前置条件 | 通用 | ✅ **同意** | flag 是"该不该考虑某动作"，与场景无关 |

**要补的一格（你表里没有）**：`POSITION_RULES` 的**分配槽位**（挡水→1、救治→2、疏散→3）也是**通用**——
它是"安全动作次序"的固定约定，不随场景变；大客流没有这三种动作，只是这三条**不触发**而已。

**结论：真正场景相关的只有 1 格 —— `TIER` 的 action_type→档号 映射。** 档数（1–5）与单调语义通用。

## 二、Q2：默认 TIER 与未配置时的行为

**默认表 = 现行常量，逐位不变**：

```
人身安全→1 · 切断危险源→1 · 关键设备→2 · 运营调整→3 · 信息报告→4 · 恢复善后→5
其余（未知 action_type）→ 6（TIER_OTHER）
```

**未配置的场景用默认**。三种"没有覆盖"的情形**全部回退默认、且不崩**：
场景未在配置文件里 / 配置文件缺失 / 配置文件损坏（对齐 `_load_pins` 的 fail-soft）。

> 这样设计的关键收益：**零回归是构造性保证**。现有 6 个场景（暴雨/脱轨/扶梯/宠物/恐袭/失火…）
> 一个都不写配置 → 行为与今天**逐字相同**。

## 三、Q3：大客流具体怎么配（当前唯一需要的实例）

```json
{ "大客流": { "tier_overrides": { "运营调整": 1 } } }
```

**理由**：大客流的核心处置是**客流管控**（客流控制点 / 限流 / 铁马 / 回形线路 / 改变扶梯走向）。
它在 schema 里落 `action_type=运营调整`，按默认是第 3 档、排在"关键设备"之后。
但在**踩踏风险**场景里，客流管控**就是人身安全本身** ⇒ 应与第 1 档同级。

覆盖后排序效果：`运营调整` 步骤升到第 1 档 → 排在第 1 档安全槽位（挡/救/疏，若有）之后、`关键设备` 之前。

**如实写清副作用**：`运营调整` 是**粗粒度**标签，会连带把"加开空车 / 调整交路"这类纯运力步骤也升档。
对 大客流 可接受（运力调整也是核心响应）。若日后发现问题，应引入更细的 `action_type`——
**那是另一次改动，不在本设计内**（本设计不碰 schema、不碰 prompt）。

大客流只写 `运营调整` 一条覆盖，`关键设备` 仍为第 2 档、其余不动。

## 四、Q4：恐袭——不单独配，用默认

**不配。** 依据（恐袭 3 次实测，全程默认 TIER）：

- 步数 `[15,14,15]`、逆序对 0、降级 0；
- 救治/疏散均占位；挡水未误触发；
- **没有暴露任何"需要改档"的问题**。

恐袭核心动作——隔离行凶者（`切断危险源`=1）、报警/疏散（`人身安全`=1）——在默认档号下**本就落在第 1 档**，无需覆盖。

按"别过度设计"：**只配被实证要求的场景**。当前只有 大客流 一个。

## 五、Q5：配置文件路径与格式

**路径**：`online/scene_tier_map.json`（与 `scene_chapter_map.json` 同目录；加载沿用同款多路径探测）。

**格式：极简，只写要覆盖的场景**：

```json
{
  "_comment": "生成层：仅登记需要覆盖默认 TIER 的场景；未列出的场景一律用默认表。",
  "大客流": { "tier_overrides": { "运营调整": 1 } }
}
```

**语义**：
```
effective_tier(action_type) = overrides.get(action_type, DEFAULT_TIER[action_type])
```
**约束**：只允许**按 action_type 覆盖档号**；不允许删档、改档数、改档序语义（保住单调性）。
不在配置里的场景 → 零覆盖。

**明确拒绝的写法**（按你的约束）：❌ 每个场景写完整五档映射。配置里出现的永远只是"差异"。

## 六、Q6：与 `scene_chapter_map.json` 的职责划分——不重叠，分文件

| 文件 | 层 | 内容 | 消费方 | 演进状态 |
|---|---|---|---|---|
| `scene_chapter_map.json` | **检索层** | `allowed` / `forbidden` / `pins`（章节过滤、pin 置顶） | `main.py` | **已封版**（`v0.3.2-retrieval-frozen`） |
| `scene_tier_map.json`（新） | **生成层** | `tier_overrides`（档号覆盖） | `plan_generator.py` | 会继续调 |

**划分原则：按"改动会动哪一层"分文件。**

- 检索层已封版、不再动；生成层的档位策略会持续迭代。
- 若并进同一个文件，**生成层每次调档都会改动那个"已封版"的文件**——封版就被污染了，回滚也牵连两层。
- 两者独立演进、独立回滚。

**唯一需要对齐的是"场景键"**：两个文件都用 `_match_scenes` 产出的场景名（如 `大客流`）。
新加载函数**复用现有场景命名**，但**不修改检索层任何代码**。

## 七、实施要点（仅备查，本次不改代码）

1. 新增 `_load_scene_tier_overrides()`：读 `scene_tier_map.json`，缺失/损坏 → 返回 `{}`（fail-soft，不崩）。
2. `TIER` 由"常量表"变为 `effective = {**DEFAULT_TIER, **overrides}`；`_tier(step)` 改为消费 effective 表。
3. **不动**排序 / 合并 / cap / KW / `POSITION_RULES` / 检索层。
4. 回归门槛：不写配置时，暴雨 + 恐袭 + 大客流 三场景输出**与今天逐字一致**；写了大客流覆盖后，验 `运营调整` 升档且逆序对仍为 0。

## 八、一句话总结

**只有 `TIER` 需要场景化，且只需 `tier_overrides` 增量覆盖；当前唯一实例是大客流的 `运营调整→1`；
配置独立成 `scene_tier_map.json`，与检索层 `scene_chapter_map.json` 分属两层、互不重叠。**
