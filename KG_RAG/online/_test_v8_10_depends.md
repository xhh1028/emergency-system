## 一、改动

### 1. schema：每步加 `depends_on`
```json
"depends_on": [1],   // **必须先完成**的步骤 n（硬先后）；没有就写 []
```

### 2. prompt 新增（十四）硬性先后必须用 `depends_on` 声明
明确三类典型必须声明的情形：**进区间依赖隔离电流** / **送医依赖现场施救** / **恢复行车依赖确认区间安全**；
约束：只写真硬先后、不得悬空/自环/成环。（标题 `十三条` → `十四条`）

### 3. `_apply_depends`：**受约束拓扑排序**
- 以现有 tier 排序的结果为 **rank（软偏好）**，以 `depends_on` 为**硬约束**；
- Kahn 算法，每次取"依赖已满足、rank 最小"的一步；
- **无依赖时 → 原顺序逐位不变**（零回归，已单测）；
- 有依赖时 → 被阻塞者**只能往后**挪，即"最小必要位移"；
- **环 / 悬空 / 自引用 → 记日志并丢弃该条坏边**，不让它把排序拖死。

### 4. 渲染
每步新增 `- 前置：需先完成 步骤N`（**经 `old2new` 重映射**，与 `parallel_with` 同款机制）。

**调用顺序**：`_order_steps` → **`_apply_depends`** → `_enforce_traction_safety`（安全规则**最后发言**）。

### ⚠️ case_003「进区间先于隔离电流」——**结果对了，但不是依赖修的**

- 最终顺序正确：`步骤5 隔离电流` → `步骤7 组织抢险人员进入区间`；
- **但 步骤7 的前置里没有 步骤5**（LLM 声明的是"依赖挡水/排水/联络"）——**LLM 漏了最关键的那条**；

⇒ **依赖机制只修"LLM 声明了的"依赖；漏声明的，它管不了。**

## 五、两套机制的关系（本轮最重要的发现）

| | 机制 | 强项 | 弱项 |
|---|---|---|---|
| **v8.10** | `depends_on` 声明 + 拓扑排序 | **通用**（任何硬先后都能表达）、能修"送医/施救""恢复/确认"这类**无关键词可枚举**的先后 | 依赖 **LLM 是否声明**；漏声明就没辙 |
| **v8.2** | 关键词安全规则（止血带） | **不依赖 LLM**，是代码硬兜底 | 只覆盖"牵引电流/进区间"那一对 |

**实测证明两者互补**：
- case_001 → 依赖声明对了 → 无需安全规则介入；
- **case_003 → 依赖排序把这条弄反了 → 被安全规则拦下并交换回来**。

⇒ **安全规则不但仍需要，而且因为依赖排序会打乱顺序，它变得更必要了**（它现在是排序后的最后一道闸）。

## 六、如实报告：逆序对 103 是不是"乱"

不是。以 **case_001（逆序对 33，最高）** 为例，逐条看下来顺序是**因果连贯**的：

```
1通知救援 → 2扣停后续列车 → 3进入紧急状态 → 4关站+PIS → 5降级运行
→ 6驾驶员报告 → 7穿行检查(前置6) → 8通知事故处理主任(前置1) → 9设事故控制站(前置8)
→ 10陪同救援人员(前置9) → 11确认隔离电流(前置9) → 12进区间疏散(前置11)
→ 13救治转运(前置10) → 14恢复行车(前置12,13) → 15调查(前置9)
```

33 处逆序来自"跨档因果被拉直"（如 信息报告(tier4) 被提到 运营调整(tier3) 之前，因为后者依赖它）。
**这是硬约束胜软偏好的必然结果，不是排序错乱。**

> 但**新风险要来**：依赖是 LLM 声明的，**声明越多、tier 顺序被改写得越多**。若哪天发现某场景"顺序被打散但因果说不通"，那就是 LLM 过度声明依赖——那时要加"依赖数量/跨度"的上限。
