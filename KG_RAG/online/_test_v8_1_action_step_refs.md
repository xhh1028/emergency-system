## 一、缺陷回顾

第二轮真实使用发现：场景 3 的 `action` / `fallback[].action` **正文内嵌"步骤N"引用**，排序/合并后未重映射、**指向错误步骤**。原文（修复前）：
```
步骤3：「…若是，进行步骤7；若否，通知值班经理，程序到此完结。」
步骤5：「…若是，进行步骤7处理可疑物品或步骤8处理有毒气体/物体；若否，进行步骤9。」
步骤7：「…若是，进行步骤10；若否，通知值班经理，程序到此完毕。」
备用行：「进行步骤7处理发现的可疑物品」「进行步骤8处理发现的有毒气体/物体」「进行步骤10」
```
**明确不做自动重映射**——自由文本里的"步骤N"用正则改写易误判（未必真指该步），**改错比不改更危险**。

## 二、改动

### 1. 校验日志（渲染层，**只警告、不改内容**）

新增 `_check_step_refs(steps, log)`（`plan_generator.py:503`），在 `_render_steps` **完成重编号后**调用（`:541`）：

- 扫描每步的 `action` 与 `fallback[i].action`（**不含 `basis`**——见 §五）；
- 正则：`步骤\s*(\d+|[一二三四五六七八九十]+)`（阿拉伯数字 + 中文数字）；
- 命中即 `log WARNING`，列出：**步骤位置 + 字段名 + 命中的原文片段 + 该编号当前指向的是哪一步**；
- 末尾汇总条数。**不修改任何文本。**

单元验证（用修复前场景 3 的原文）：命中 **7 处**，逐条正确指出"步骤7 → 现指向'公安部门负责人判断是否须作进一步搜索'"、以及"步骤8/9/10 → 不存在此步"；
中文数字转换 `十一 → 11`、`七 → 7`、`二十一 → 21` 均正确。

### 2. prompt 约束（硬性约束区新增（十二））

```
（十二）不要用"步骤N"引用其他步骤
`action` 与 `fallback[].action` 正文里**一律禁止出现"步骤N"式的交叉引用**。
如需表达"处理完 A 后进入 B"，改用文字描述（如"完成搜索后按本方案对应程序处理"）。
理由：步骤会经排序/合并重新编号，正文里写死的编号会随之失效、指向错误步骤。
```
标题同步：`以下十一条` → **`以下十二条`**。

## 四、结论

**校验 + prompt 约束路线成立**：约束加在源头，LLM 不再产出编号引用，校验器一次都没被触发。
按裁定，**本轮不做自动重映射**——既然约束后已 0 命中，重映射暂不需要设计。

> ⚠️ **n=3 通过 ≠ 永久解决。** 这三次命好，不是保证——回顾 v6：救治曾 5/5、疏散却 4/5，
> LLM 偶尔就是不遵守约束。所以本次加的两件是**双保险**：
> **prompt（十二）负责从源头不发**，**`[step-ref]` 校验日志负责万一又发了能报出来**。
> 将来若再看到 `[step-ref]` 告警，**那是兜底在正常工作，不是回归**——不要因为这次 n=3 就误判为已根除。

## 五、一处边界说明（**不是缺陷**）

`依据：AIEP08 8B3 [步骤7]` 里的"步骤7"是**源规程文档自身**的步骤号（schema 的 `basis` 字段），
**不是**本方案步骤号，**不应重映射、也不在扫描范围内**。校验器只扫 `action`/`fallback[].action`，边界正确。
（最初用整段文本粗扫时曾误报这些，复核后确认属误判。）
